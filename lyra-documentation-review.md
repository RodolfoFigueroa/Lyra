# Lyra documentation review

Reviewed on November 2, 2026. Scope: all 41 authored site pages, navigation and content plans, the organization of the generated references, the root README and contributor guide, example documentation and implementations, the portable authoring skill and its bundled references, and the benchmark guide. This is a structural and instructional review. I did not perform an API accuracy audit or execute the examples. Project files are unchanged.

The main recommendation is to preserve the existing audience-based organization and make page responsibilities clearer. Add a coherent plugin-development tutorial alongside independent task guides, concepts, and reference material. Most of the work should be redistribution and connection of existing material; selected learning pages need substantial rewriting.

The documentation already has useful foundations: distinct consumer, author, and operator sections; task-oriented titles; content types and matching editorial plans; executable examples; source-backed snippets; isolated example tests; and generated contracts. Preserve those mechanisms. The largest weaknesses are the discontinuous learning path, advanced topics hidden inside broader pages, and explanations repeated across pages with different stated purposes.

I would retain the six principal documentation areas, with these responsibilities:

| Area | Responsibility and internal organization |
| --- | --- |
| Start here | Explain Lyra, choose an execution mode, install the needed components, and reach a first local or server result. Give readers explicit onward paths for consuming metrics, writing plugins, and operating deployments. |
| Run metrics | Independent guides for local execution, Python, HTTP, MCP, selecting locations and editions, observing jobs, interpreting provenance, and retrieving results. Readers can use these without writing a plugin. |
| Build plugins | An overview with two branches: the sequential city-analysis tutorial and independent task guides. Group guides around calculations and outputs; graph composition; locations and sources; testing and delivery. Agent-assisted authoring is an optional workflow. |
| Deploy and operate | Deployment, resource configuration, authentication and networking, plugin enablement and routing, monitoring, updates, cache administration, and symptom-based troubleshooting. |
| Understand Lyra | Focused explanations of the basic model; source identity and editions; graph execution; canonical selection versus calculation dependencies; caching, revisions, and provenance; job lifecycle; and architecture. Avoid making readers complete this section before running anything. |
| Reference | Curated Python API entry points, complete generated contracts, parameter and handler rules, table and location contracts, units, routing and binding rules, and artifacts. Reference pages support precise lookup independently of the tutorial. |

Contributor setup, release procedures, benchmark maintenance, and documentation-authoring instructions should remain contributor material. Link to them from the site or footer. They need not occupy the product-learning path.

The Build Plugins overview should route three common readers: someone building a first plugin, someone adapting an existing calculation, and someone extending an existing plugin. Offer the tutorial to the first reader and relevant task guides to the others.

For the storyline, I recommend a small city-analysis plugin using streets, blocks, and their explicit membership relationships. The existing city fixtures already supply most of the needed mechanisms. Use a transparent demonstration calculation and state what its values mean. The tutorial should teach Lyra without requiring readers to learn a real scientific scoring methodology.

The core sequence would be:

| Chapter | Developer need | New Lyra capability | Working checkpoint |
| --- | --- | --- | --- |
| 1. Expose and run a calculation | Make an existing Python calculation callable through a declared contract. | A metric, named output, PluginDefinition, and LocalRunner. | Run a calculation over a tiny fixed fixture and inspect its identified output rows. |
| 2. Let callers choose streets | Run the same calculation for selected entities. | ID selections, Locations, a concrete location contract, and a small in-memory provider. | Select known street IDs and show how the handler receives resolved locations. Explain the supplied provider before asking readers to customize it. |
| 3. Make the calculation configurable and interpretable | Let callers choose ordinary calculation options and understand returned values. | Parameter models, defaults, output validation, units, descriptions, and optionally multiple named outputs. | Change a parameter, compare results, and verify an invalid request or result with an isolated test. |
| 4. Reuse a calculation in another report | Build several reports from the same intermediate table. | Dependency, producer/output names, forwarding, and private intermediate metrics. | Execute a composed graph, inspect its diagram, and demonstrate shared work without adding a service. |
| 5. Derive the locations a report needs | Produce a block report without requiring callers to enumerate every street. | A noncanonical location operation, LocationDependency, and explicit membership/weight tables. | Select blocks, derive streets, and explicitly aggregate street results into block rows. Include a block with no related streets. |
| 6. Accept another way to select the same calculation | Allow callers to select blocks when requesting street results. | Canonical operations and accepted selections. | Run the street metric through block selections and show that its output still contains street rows. Compare it with chapter 5's explicitly aggregated block result. |
| 7. Inspect and verify the complete graph | Explain how a result was produced and diagnose failures. | Provenance inspection, native inputs, graph diagnostics, and orchestration tests. | Inspect a run and check known results, empty intermediates, and a failing boundary. Small tests should already appear in earlier chapters. |
| 8. Prepare the plugin for sharing | Give another developer or operator an inspectable, reproducible plugin. | Package metadata, factory registration, generated manifest, and freshness checks. | Finish with a locally verified package and an explicit operator handoff. Link to deployment and consumer guides for the optional server continuation. |

Chapters 5 and 6 are the most valuable instructional comparison. Deriving locations for a block calculation and accepting blocks as a public selection for a street calculation solve different needs. The same domain and fixtures make that difference visible. Preserve the membership table when aggregation needs it: a union of selected streets does not contain the block-to-street attribution.

Keep these extensions outside the required core sequence:

| Extension | Motivating need | Scope |
| --- | --- | --- |
| Independent supporting context | Score a selected street using a broader surrounding selection. | Two named location inputs, forwarding, and the distinction between result entities and context. |
| Metric editions | Preserve separately selectable data or methodological variants under one stable family contract. | Factories, concrete dependency bindings, edition metadata, and family compatibility. Distinguish editions from ordinary caller parameters. |
| File and service resources | Replace fixtures with maintained data. | Introduce a local file resource first; offer database and Earth Engine integrations as independent recipes. |
| Persistent reuse and revisions | Avoid repeating work and respond deliberately to changed data. | Cache configuration, location revision coverage, cache_revision, and observed reuse. |
| Constructed locations | Analyze sites or buffers created by the calculation. | Table-to-location conversion, distinct entity identity, projected geometry operations, and nested bindings. |
| Competing canonical routes | Combine plugins that offer equally short routes. | Route preferences, ambiguity, and the effect of shortcuts. This is a deployment/composition concern rather than a prerequisite for a first plugin. |

Each extension should name the checkpoint it starts from and remain readable as a task guide. A reader who only needs editions or resource injection should not have to reconstruct the whole tutorial.

For examples, use one shared domain and vocabulary without requiring every page to use the same full graph. A dependency recipe needs only a producer, a consumer, and a table. A reference example can be smaller still. Keep purpose-specific fixtures when they isolate a mechanism more clearly.

Promote the city example into an intentional documentation package with a readable README, known requests, expected results, and visible registration. The existing smoke plugin can continue serving smoke/integration tests. The diagram-preview fixture belongs with renderer/contributor material. Those fixtures need not all become the public teaching project.

Provide chapter checkpoints that run independently, preferably with named factories or a small checkpoint layout. Show the registration used at each checkpoint rather than loading a final factory that silently includes future capabilities. Keep the final package organized by understandable responsibilities rather than by tutorial chapter number alone.

Use source-backed snippets where they help keep the guide and runnable code together. Continue explaining the important code inline; a link to a complete source file is supplementary. Keep boilerplate out of repeated lessons through shared fixtures whose definitions have already been explained. Choose one primary Pandera declaration style for the tutorial and describe alternatives in the output guide.

Consumer examples should use the finished tutorial plugin, known IDs, and meaningful output names across Python, HTTP, and MCP. Show submission and retrieval directly. Tests can verify these workflows with in-process transports without becoming the reader's primary interface to them.

For generated references, preserve generation and downloadable schemas. The MCP reference already combines readable top-level field tables with expandable complete schemas; that is a useful pattern. Do not judge its size by raw source line count. Improve the HTTP reference by linking named response models to readable schema details, rather than making a raw OpenAPI download the only destination for nested contracts. Keep the complete module browser while adding curated Python entry points such as metric definition, plugin registration, local execution, locations, resources, client submission, and result access.

Introduce a small decision table explaining the identities that currently recur across guides. A metric edition selects a metric variant; a source contract identifies an observation; a geographical edition identifies boundaries and unit identities; a data revision identifies a maintained correction/version within a contract; cache_revision supplies caller-controlled run-wide invalidation. Explain their relationships with one worked city example. Preserve these distinctions in reference, but keep the full taxonomy out of the first definition of a metric.

The portable skill is a separate documentation product with a valid self-contained use case. Preserve its local authoring contract and compatibility workflow. Align terminology and reusable examples with the human docs, while allowing the skill to remain compact instructions for adaptation rather than a progressive tutorial. Shared mechanical tables and snippet sources can reduce drift without requiring an installed skill to fetch the website.

The writing-guidelines review supports the structural changes more strongly than a broad sentence-level rewrite. Existing task titles, sentence-case headings, short snippets, descriptions, and content plans are useful. The recurring readability issue is the number of concepts introduced together and the movement between tutorial, explanation, and contract rules. Apply the guidance about one page purpose, defined terms, explained examples, and reader-shaped goals. Preserve Lyra's Python and documentation-tool conventions rather than importing Vercel-specific framework requirements.

For future authoring, use a page's content plan to record its reader, prerequisite knowledge, concrete outcome, content type, and owning topics. A tutorial should identify its starting checkpoint, changed code, runnable command, and expected result. A task guide should state prerequisites and show its complete procedure. A concept page should explain decisions and relationships. Reference should expose exact contracts and limits. Keep consequential constraints close to the relevant step even when the complete rule lives elsewhere.

Implement the proposal in this order:

1. Agree on page responsibilities, the six-area navigation, the city domain, and example naming. Assign one primary owner to each topic while allowing brief context and links elsewhere.
2. Build and verify the first three tutorial checkpoints. Use them to settle the amount of setup, terminology, and provider explanation before extending the entire series.
3. Complete the core graph and canonical-selection comparison, then packaging and the optional extensions. Integrate tests and inspection throughout.
4. Split the overloaded pages and move their material into the agreed task, concept, and reference destinations. Update links and preserve useful existing URLs through redirects where needed.
5. Align consumer examples, deployment verification, example READMEs, the reference chooser, and the portable skill's shared terminology.
6. Update the existing content plans, navigation, and documentation-authoring guidance. Verify links, rendering, schemas, and executable examples using the project environment and in-process fakes. Editorial choices should be reviewed as documentation rather than pinned by wording tests.

Evaluate the result with concrete reader tasks: create and run a first metric; adapt an existing function; add an explicit dependency; derive a location input; expose canonical selection; register an edition; configure a resource; interpret a result; and enable the package in a deployment. Each reader should be able to reach the relevant task independently, with the tutorial available when they want a guided progression.
