Use an existing Lyra server to calculate maintenance workload for a street. You’ll find the calculation, submit one job, and check its status before downloading the result. If you want to try the same example before setting up a server, start with [your first local metric](../start/local/).

Before you start, obtain these details from your operator:

- The address of a running Lyra server
- An agent key
- Access to `city_street_maintenance` from the example `lyra-city-example`

The city plugin includes the data for this example. `street-1` is 100 m long and has a condition score of 20, so it needs maintenance at the default threshold of 50. If you use a different metric, inspect which selections it accepts and choose valid IDs for its dataset. Follow [Deploy Lyra](../operate/deployment/) if you need to set up the server.

<Steps>

1. ## Set server details <span id="set-your-connection-details"></span><span id="set-your-connection-details-"></span><span id="1-set-your-connection-details"></span>

   In your shell, set the server address and the agent key. Replace the values with your operator’s address and key:

   ```sh
   export LYRA_URL="http://localhost:5219"
   export LYRA_AGENT_API_KEY="your_agent_key_here"
   ```

   For a remote deployment, use an address beginning with `https://` to encrypt traffic. An agent key permits job operations; the separate administrator key is for operators.

1. ## Check the available metric <span id="2-check-the-available-metric"></span>

   List the available metrics, then inspect the maintenance metric’s input and output declarations:

   ```sh
   curl "$LYRA_URL/metrics"
   curl "$LYRA_URL/metrics/city_street_maintenance"
   ```

   The first response lists the available calculations. In the second response, check `accepted_selections` for supported datasets and feature types. Then check `parameters` for threshold settings. These fields describe the example’s request and result:

   - `native_inputs`: the locations the calculation uses, here streets
   - `parameters`: settings you can change and their allowed values
   - `outputs`: the result tables and their columns
   - `bindings`: the data sources and versions required by the calculation
   - `accepted_selections`: the datasets and feature types you can select

   Check that `streets` accepts the `street` unit type from `example:city`. The optional `condition_threshold` parameter accepts integers from 0 to 100 and defaults to 50. For named editions, inspect with `?edition=your_edition_here` and include the same top-level `edition` in the job request.

   If this metric is absent, ask the operator which metric to use and follow its advertised schema. Metric availability depends on the server’s enabled plugins.

1. ## Submit one job <span id="3-submit-one-job"></span>

   Send the metric name, ID selection, and parameter value in one submission:

   ```sh {6-11}
   curl -X POST "$LYRA_URL/jobs" \
     -H "Authorization: Bearer $LYRA_AGENT_API_KEY" \
     -H 'Content-Type: application/json' \
     -d '{
       "metric": "city_street_maintenance",
       "input": {
         "streets": {
           "collection": "example:city",
           "unit_type": "street",
           "ids": ["street-1"]
         },
         "parameters": {"condition_threshold": 50}
       }
     }'
   ```

   The server validates request structure before accepting the job. Workers resolve the selected IDs during execution; unknown IDs fail the job. The accepted response includes a `job_id`. Copy it into a shell variable:

   ```sh
   export JOB_ID="your_returned_job_id_here"
   ```

   Each submission creates a new job. If the request times out, the server may already have accepted it. Check the outcome before deciding to submit again.

1. ## Wait for completion <span id="4-wait-for-completion"></span>

   Use the saved job ID to check the same job’s status:

   ```sh
   curl "$LYRA_URL/jobs/$JOB_ID" \
     -H "Authorization: Bearer $LYRA_AGENT_API_KEY"
   ```

   Repeat the status request roughly every five seconds while the status is `queued` or `running`. A successful job reports `succeeded`. A failed job reports `failed` and an error; use [job troubleshooting](../use/jobs/#handle-a-failed-job) before starting another execution.

   Progress may be absent. Use the job status to determine whether execution has finished.

1. ## Inspect and download the result <span id="5-inspect-and-download-the-result"></span>

   Once the job succeeds, inspect its output summary and save the complete JavaScript Object Notation (JSON) result:

   ```sh
   curl "$LYRA_URL/jobs/$JOB_ID/result/inspection" \
     -H "Authorization: Bearer $LYRA_AGENT_API_KEY"

   curl "$LYRA_URL/jobs/$JOB_ID/result/download" \
     -H "Authorization: Bearer $LYRA_AGENT_API_KEY" \
     -o result.json
   ```

   The inspection lists output names and row counts, plus the time remaining before the result expires. In `result.json`, find `outputs.maintenance`. Its row identifies `street-1`, with `length_m` and `maintenance_length_m` both equal to 100. The entire street needs work because its condition score, 20, is below your threshold of 50.

   Save results you need before they expire. The download includes output descriptions and [provenance](../concepts/provenance/), which records the request and execution.

</Steps>
