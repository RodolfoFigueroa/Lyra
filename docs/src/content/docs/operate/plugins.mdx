Enabling a plugin requires two things: its distribution must be installed in the image, and its entry must be selected in `lyra.toml`. Installing a package alone does not publish its metrics.

<Steps>

1. ## Add the dependency to the deployment <span id="1-add-the-dependency-to-the-deployment"></span>

   Add the plugin and its sources to the deployment project’s dependencies. Update and commit the lockfile, then rebuild the image.

   The example has separate production and development dependency sets. When changing its packages, update both locks from `examples/lyra-deployment`:

   ```sh
   uv lock
   uv lock --project dev
   ```

   All API and worker containers use the same selected package versions. Include every transitive dependency plugin and any native libraries the runtime needs. Private source credentials belong to the image build configuration.

1. ## Select the installed distribution <span id="2-select-the-installed-distribution"></span>

   ```toml
   [[plugins.installed]]
   distribution = "my-plugin"
   enabled = true

   [plugins.installed.routing]
   expensive_metric = "batch"
   ```

   The API reads the distribution’s manifest from its installed shared-data path. Workers load factories for their public roots and dependencies, then compare the definitions with those manifests. Disabled entries are not loaded.

   An enabled routing override must name a metric in the plugin manifest. All queues must appear in `plugins.allowed_queues`. Metrics without an override use `plugins.default_queue`.

1. ## Cover every routed queue <span id="3-cover-every-routed-queue"></span>

   Configure a worker pool to consume each assigned queue:

   ```toml
   [workers.batch]
   queues = ["batch"]
   concurrency = 2
   ```

   The requested metric’s queue selects the worker for its entire graph. Dependencies execute on that worker, even when their metrics use different queues for direct requests.

   After a safe restart, inspect `lyra-admin plugins list`, `lyra-admin routing list`, `lyra-admin workers list`, and `lyra-admin queues list`. A published catalog entry alone does not establish that a worker can import and execute the plugin.

</Steps>

## Develop with editable sources

From `examples/lyra-deployment`, use the checked-in override:

```sh
docker compose -f compose.yml -f compose.dev.yml up -d --build
```

Configure the census plugin’s `census_db` resource in `lyra.dev.toml` before starting the containers.

The override mounts application and plugin checkouts at their editable installation paths. Its absolute `manifest_path` points to the generated manifest in the mounted plugin checkout. Install the distribution even when you mount its source.

Keep container dependencies in `/app/.venv`; mount source checkouts without replacing that environment with a host virtual environment. Source edits require manual process restarts; use the [change table](../updates/#choose-the-required-update).

After changing a metric contract, regenerate and check its manifest from the Lyra repository root:

```sh
uv run lyra-plugin build-manifest --project examples/lyra-plugin
uv run lyra-plugin check-manifest --project examples/lyra-plugin
```

Restart the API and workers after updating the manifest. Workers reject manifests that differ from imported definitions.

## Add another checkout

For an independently maintained plugin:

1. Add the distribution and source to both dependency sets; make the development source editable.
2. Add a named Compose build context for its checkout.
3. Copy that context into the Dockerfile’s source stage, preserving relative dependency paths.
4. Add a matching development mount to API and worker services.
5. Enable the distribution in both TOML files; set a development `manifest_path`.
6. Generate the manifest, update locks, and rebuild.

`LYRA_SOURCE` and `SMOKE_PLUGIN_SOURCE` identify the example checkouts. For another plugin, choose source and container paths that resolve consistently during locking and image builds.

For a plugin checkout beside the Lyra repository, use these paths in the example deployment:

| Setting | Path |
| --- | --- |
| Production uv source | `../../../other-plugin` |
| Development uv source | `../../../../other-plugin` |
| Container source and development mount destination | `/workspace/other-plugin` |

Copy each build context into the Dockerfile’s `sources` stage and mount its checkout read-only during development. Add native libraries required by the plugin to the runtime stage.

Commit both lockfiles and source changes: local path locks pin dependencies but do not pin checkout contents. For production Git dependencies, pin full commit IDs and declare the SDK and utilities’ repository subdirectories at the same commit. Supply private dependency credentials during image builds.

Apply changes with the [safe update procedure](../updates/).

## Enable a location provider

Install and enable exactly one provider plugin for spatial requests. Provider-only plugins need no metric routing entries.

Configure the provider’s resource under `[resources.resource_name.config]` and `[resources.resource_name.secrets]`. Replace `resource_name` with the resource name declared in the manifest. Workers need the provider’s dependencies and credentials to resolve selections during execution.

Inspect `location_collections` in `GET /metrics` to find supported collection names, unit types, and coordinate reference systems. Callers submit ID selections; workers resolve them in the execution resource scope and close the provider after execution. See [Define a location provider](../../plugins/location-providers/) for the resource contract.
