To enable a plugin, install its distribution in the deployment image and select its entry in `lyra.toml`. Installing a package alone does not publish its metrics.

<Steps>

1. ## Add the dependency to the deployment <span id="1-add-the-dependency-to-the-deployment"></span>

   Add the plugin and its sources to the deployment project’s dependencies. Update and commit the lockfile, then rebuild the image.

   The example has separate production and development dependency sets. When changing its packages, update both locks from `examples/lyra-deployment`:

   ```sh
   uv lock
   uv lock --project dev
   ```

   Use the same package versions in API and worker containers. Include every dependency plugin and any native libraries the plugins need. Configure credentials for private sources during the image build.

1. ## Select the installed distribution <span id="2-select-the-installed-distribution"></span>

   Enable the installed distribution and assign its expensive metric to the `batch` queue:

   ```toml
   [[plugins.installed]]
   distribution = "your_plugin_name_here"
   enabled = true

   [plugins.installed.routing]
   expensive_metric = "batch"
   ```

   Each enabled distribution registers a factory named `plugin` in the `lyra.plugins` entry-point group. The API and workers import this factory at startup.

   Install the plugin’s dependencies in the API and worker containers. Lyra skips disabled plugins and stops startup if an enabled plugin fails to import.

   An enabled routing override must name a registered metric in the plugin. All queues must appear in `plugins.allowed_queues`. Metrics without an override use `plugins.default_queue`.

1. ## Cover every routed queue <span id="3-cover-every-routed-queue"></span>

   Configure a worker pool to consume each assigned queue:

   ```toml
   [workers.batch]
   queues = ["batch"]
   concurrency = 2
   ```

   The requested metric’s queue selects the worker for its entire graph. Dependencies execute on that worker, even when their metrics use different queues for direct requests.

   After a safe restart, check plugin and worker coverage:

   ```sh
   uv run lyra-admin plugins list
   uv run lyra-admin routing list
   uv run lyra-admin workers list
   uv run lyra-admin queues list
   ```

   The API and workers validate plugin definitions and dependencies at startup. Check their startup logs for validation errors.

</Steps>

## Enable a location provider

Enable the plugins that register the providers your metrics require. Each public provider ID must identify one registration. A plugin that registers only providers needs no metric queue assignments.

If the provider declares settings or secrets, configure them under `[resources.resource_name.config]` or `[resources.resource_name.secrets]`. Replace `resource_name` with the resource name your plugin registers. The example providers `city_streets` and `city_blocks` read bundled data and need neither entry.

Run `lyra-plugin describe` in the plugin project to inspect its provider IDs and record schemas. On the server, list public metrics with `GET /metrics`. Use `GET /metrics/{name}` to [check which providers a metric accepts](../../use/rest-api/#read-the-live-contract).

Callers submit ID selections. Workers resolve them in the execution resource scope and close the provider after execution. See [Define a location provider](../../plugins/location-providers/) for the resource contract.
