Install your plugin in the image that the API and workers share. Then add its distribution name to `lyra.toml` so callers can request its metrics.

<Steps>

1. ## Add the dependency to the deployment <span id="1-add-the-dependency-to-the-deployment"></span>

   Add the plugin and its source to the deployment project’s dependencies. From `examples/lyra-deployment`, update the lockfile.

   ```sh
   uv lock
   ```

   Commit the lockfile and rebuild the shared API and worker image. Include every dependency plugin and any native libraries the plugins need. Configure credentials for private sources during the image build.

1. ## Select the installed distribution <span id="2-select-the-installed-distribution"></span>

   Add the installed package to `lyra.toml`. Use its Python distribution name.

   ```toml
   [[plugins.installed]]
   distribution = "your_plugin_distribution_here"
   ```

   Each enabled distribution registers a factory named `plugin` in the `lyra.plugins` entry-point group. The API and workers import this factory at startup.

   Install the plugin’s dependencies in the API and worker containers. Lyra skips disabled plugins and stops startup if an enabled plugin fails to import.

1. ## Configure the worker service <span id="3-configure-the-worker-service"></span>

   Set `worker.concurrency` in `lyra.toml` to choose how many graphs the worker service can run at once. This example starts six processes.

   ```toml
   [worker]
   concurrency = 6
   ```

   Each process takes the next job from the shared queue and runs its [whole dependency graph](../../concepts/graphs/#run-sequentially-on-one-worker). If all six are busy, even a short job waits.

   After [restarting the deployment](../updates/#drain-and-restart), use the [administrative CLI](../admin-cli/) to verify the change.

   ```sh
   uv run lyra-admin --json plugins list
   uv run lyra-admin --json queue show
   ```

   Look for your distribution with `enabled` set to `true` and at least one worker ID in `observed_workers`. If either service fails to start, check its logs for plugin validation errors.

</Steps>

## Run a local plugin server <span id="develop-with-editable-sources"></span><span id="add-another-checkout"></span>

Run `uv run lyra-plugin dev` from your plugin checkout. To test several plugins together, [add another checkout to the local session](../../plugins/development/#add-another-checkout).

## Enable a location provider

Enable the plugins that register the providers your metrics require. Each public provider ID must identify one registration.

If the provider declares settings or secrets, configure them under `[resources.resource_name.config]` or `[resources.resource_name.secrets]`. Replace `resource_name` with the resource name your plugin registers. The example providers `city_streets` and `city_blocks` read bundled data and need neither entry.

Run `lyra-plugin describe` in the plugin project to inspect its provider IDs and record schemas. On the server, list public metrics with `GET /metrics`. Use `GET /metrics/{name}` to [check which providers a metric accepts](../../use/rest-api/#read-the-live-contract).

Callers submit ID selections. Workers resolve them in the execution resource scope and close the provider after execution. See [Define a location provider](../../plugins/location-providers/) for the resource contract.
