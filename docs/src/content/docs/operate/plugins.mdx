To enable a plugin, install its distribution in the deployment image and select its entry in `lyra.toml`. Installing a package alone does not publish its metrics.

<Steps>

1. ## Add the dependency to the deployment <span id="1-add-the-dependency-to-the-deployment"></span>

   Add the plugin and its sources to the deployment project’s dependencies. Update and commit the lockfile, then rebuild the image.

   The example has separate production and development dependency sets. When changing its packages, update both locks from `examples/lyra-deployment`:

   ```sh
   uv lock
   uv lock --project dev
   ```

   All API and worker containers use the same selected package versions. Include every transitive dependency plugin and any native libraries the runtime needs. Private source credentials belong to the image build configuration.

1. ## Select the installed distribution <span id="2-select-the-installed-distribution"></span>

   Enable the installed distribution and assign its expensive metric to the `batch` queue:

   ```toml
   [[plugins.installed]]
   distribution = "your_plugin_name_here"
   enabled = true

   [plugins.installed.routing]
   expensive_metric = "batch"
   ```

   The API reads the distribution’s manifest from its installed shared-data path. Workers load factories for their public roots and dependencies, then compare the definitions with those manifests. Lyra skips disabled entries.

   An enabled routing override must name a metric in the plugin manifest. All queues must appear in `plugins.allowed_queues`. Metrics without an override use `plugins.default_queue`.

1. ## Cover every routed queue <span id="3-cover-every-routed-queue"></span>

   Configure a worker pool to consume each assigned queue:

   ```toml
   [workers.batch]
   queues = ["batch"]
   concurrency = 2
   ```

   The requested metric’s queue selects the worker for its entire graph. Dependencies execute on that worker, even when their metrics use different queues for direct requests.

   After a safe restart, check plugin and worker coverage:

   ```sh
   uv run lyra-admin plugins list
   uv run lyra-admin routing list
   uv run lyra-admin workers list
   uv run lyra-admin queues list
   ```

   A published catalog entry alone does not establish that a worker can import and execute the plugin.

</Steps>

## Enable a location provider

Install and enable exactly one provider plugin for spatial requests. Provider-only plugins need no metric routing entries.

If the provider declares settings or secrets, configure them under `[resources.resource_name.config]` or `[resources.resource_name.secrets]`. Use the resource name from the manifest. The city provider `city_data` reads bundled data and needs neither entry.

Inspect the provider’s collections and concrete contracts with `lyra-plugin describe`. Consumers list public families with `GET /metrics`. For concrete bindings and accepted source types, inspect `GET /metrics/{name}?edition=your_edition_here`. Omit `edition` for an implicit variant.

Callers submit ID selections. Workers resolve them in the execution resource scope and close the provider after execution. See [Define a location provider](../../plugins/location-providers/) for the resource contract.
