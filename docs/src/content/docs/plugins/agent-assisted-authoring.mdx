The `lyra-metric` skill guides a coding agent through adapting a Python workflow to Lyra. It can create a plugin or add a metric to an existing one.

An agent skill is a folder of instructions and supporting files for your coding agent. A Lyra plugin is the Python package that exposes the calculation. You install the skill in the agent, then work on the plugin in your project.

<Steps>

1. ## Install the complete skill <span id="1-install-the-complete-skill"></span>

   Obtain `skills/lyra-metric/` from a product release tag (`vX.Y.Z`) or a chosen repository commit. Keep the whole directory:

   ```text
   lyra-metric/
     SKILL.md
     references/
       authoring.md
       capabilities.md
     scripts/
       __init__.py
       check_compatibility.py
   ```

   Install the folder in the skill directory your agent reads. For an agent configured to read project skills from `.agents/skills/`, copy the complete folder from your chosen checkout, replacing `/your_lyra_checkout_here` with its absolute path:

   ```sh
   mkdir -p .agents/skills
   cp -R /your_lyra_checkout_here/skills/lyra-metric .agents/skills/
   ```

   If your agent uses another location, copy the same complete folder there and follow its discovery instructions. Record the source revision because installed copies don’t update automatically; when updating, replace the whole folder so its instructions, bundled contract, and helper stay together.

   The skill works from another workflow or plugin repository. It does not require a Lyra checkout there.

1. ## Prepare the workflow environment <span id="2-prepare-the-workflow-environment"></span>

   Declare `lyra[sdk]` and the calculation’s dependencies in your plugin project. Add `lyra[runtime]` to its development dependencies for the compatibility check and local execution tests.

   Give the agent your existing documentation and tests. Include a small input with a known result if you have one.

   Identify any files, databases, or external services the calculation reads. Tell the agent how to replace those reads with fixtures or fakes for local tests.

   Initialize Earth Engine in a plugin resource’s `setup()` method. Keep imports, factories, and manifest generation free of initialization and credential access. Follow [Use Earth Engine in metrics](../earth-engine/) for resource configuration and cleanup.

1. ## Check the authoring environment <span id="3-check-the-sdk-contract"></span>

   Run the compatibility check from your plugin project. Replace the script path if you installed the skill elsewhere.

   ```sh
   uv run python .agents/skills/lyra-metric/scripts/check_compatibility.py
   ```

   The script reports the installed Lyra version and checks that it can import the software development kit (SDK) and local runner. It uses a synthetic plugin to build locations, validate parameters, and generate a manifest.

   | Exit code | Meaning |
   | --- | --- |
   | 0 | The authoring environment passed the checks |
   | 1 | The script found a contract mismatch |
   | 2 | The script couldn’t complete the check |

   If the check fails, use its diagnostic and the bundled authoring reference to resolve the failure before writing the adapter. After it passes, test your own plugin against the original calculation and generate its manifest.

1. ## Give the agent a concrete request <span id="4-give-the-agent-a-concrete-request"></span>

   For a new plugin:

   > Use the `lyra-metric` skill to adapt `calculate_flood_risk` in `flood_risk.py` into a new Lyra plugin. Preserve its calculation. Read the existing documentation and tests, and ask me about missing scientific or contract details before implementing behavior that depends on them.

   For an existing plugin:

   > Use the `lyra-metric` skill to add `calculate_flood_risk` from `flood_risk.py` to this plugin. Follow its conventions, retain the existing metrics, and ask about missing information needed to define the new metric.

   The agent creates the adapter, models, output declarations, explicit dependencies, factory registration, manifest, and tests as appropriate. Compare the adapter’s results with the original calculation to check that the behavior matches.

1. ## Resolve questions that affect the calculation <span id="5-resolve-questions-that-affect-the-calculation"></span>

   The agent should use code, tests, documentation, and your answers as evidence. It must ask when conflicting or missing information affects the calculation, public contract, or interpretation of results.

   For example, if the calculation can return different columns for different parameter values, agree on a fixed output schema. Resolve unknown units, missing-data behavior, and spatial resolution before the agent writes code that depends on those choices. It can continue work independent of those decisions.

   Handlers receive named feature collections with a coordinate reference system (CRS). These collections support points, lines, polygons, and their multipart variants. Public execution requests contain ID selections.

   Preserve existing reprojection when the calculation needs it. Missing coverage documentation alone does not establish either a restriction or universal validity.

1. ## Review the handoff <span id="6-review-the-handoff"></span>

   Review the adapter and tests alongside `lyra-plugin describe` and the generated manifest. Check spatial assumptions, result meanings, and evidence for changes.

   [Useful descriptions](../descriptions/) explain what consumers need to choose inputs and interpret results. Known scientific limitations belong in metadata; incomplete verification belongs in the handoff.

   Check that the handoff includes:

   - Changed files
   - Checks and their results
   - Unresolved questions
   - Checks that unavailable data or services prevented

   Review the adapter against the original calculation before publishing it.

   When ready, [package the plugin](../publish-and-debug/). Publishing and deployment remain separate steps.

</Steps>
