Declare a dependency when your calculation needs a table from another metric. Name the producer and its output, then map them to the handler argument that receives the table. The following complete adapter uses the city project’s bundled data and requires no service.

## Declare the table graph

In the [prepared city project](../tutorial/), create `maintenance_graph.py` with these imports:

```python title="maintenance_graph.py"
import pandas as pd
from lyra.sdk import (
    Dependency, LocalRunner, Locations, PluginDefinition, metric,
)
from city_example.calculations import calculate_maintenance
from city_example.metrics import (
    MaintenanceParameters, street_conditions, street_lengths,
)
from city_example.provider import CityLocationProvider
from city_example.schemas import MAINTENANCE, STREETS
```

Append the consumer. Its two named table inputs come from the length and condition producers:

The condition producer is private because it is an intermediate table. Both producers accept the same `streets` contract, so the consumer forwards that input by name. The threshold belongs to the maintenance calculation and needs no upstream forwarding.

## Register and run the graph

Append the producer registrations, provider, and request:

```python title="maintenance_graph.py"
plugin = PluginDefinition(
    metrics=[street_lengths, street_conditions, street_maintenance],
    resources={"city_data": CityLocationProvider},
    location_provider="city_data",
)
runner = LocalRunner.from_definitions({"city": plugin})
tables = runner.run("city_street_maintenance", {
    "streets": {
        "collection": "example:city", "unit_type": "street",
        "ids": ["street-1"],
    },
})
```

Run `uv run python maintenance_graph.py`. `tables["maintenance"]` identifies `street-1` and reports 100 m of maintenance workload. Dependencies can cross plugins without importing their implementations; enable every required producer plugin.

## Forward or rename parameters <span id="3-forward-or-rename-parameters"></span>

A producer’s ordinary fields resolve in this order:

1. An explicit override in the dependency declaration
2. A matching effective parameter on the consumer, including its defaults
3. The producer’s own default
4. Failure, if a required value is still missing

Matching ordinary parameter names forward automatically. For a producer that accepts `year`, a consumer can explicitly map its own `baseline_year` field as follows:

```python
from lyra.sdk import Dependency, Input

inputs = {
    "records": Dependency(
        "example_selected_records", producer="example_selected_source",
        parameters={"year": Input("parameters.baseline_year")},
    ),
}
```

An `Input` path refers to a field declared by the metric or operation that owns the dependency declaration.

Use `parameters=` and `locations=` to bind invocation inputs. Parameter overrides replace whole fields, including nested objects, and explicit `None` counts as a supplied value. Bindings cannot supply tables or contexts.

## Forward the required spatial inputs <span id="4-forward-the-required-spatial-inputs"></span>

Graph validation checks explicit location bindings before matching names. To supply a producer’s `streets` input from a consumer’s `selected_streets` selection, declare:

```python
locations={"streets": Input("selected_streets")}
```

Declare both names as location inputs on their respective metrics. A consumer may declare an input solely to forward it to a dependency.

Use `Input` references or nested `LocationDependency` declarations for location bindings. Bindings cannot supply literal values. If names differ, declare a binding even when both arguments use `Locations`.

Supplied locations must match the receiving input’s concrete location contract, whether you bind them explicitly or forward matching names. For nested operations, declare that contract as the operation’s output. Lyra rejects incompatible contracts during graph validation.

Public canonical selection resolves the root metric’s native inputs before forwarding. It does not change calculation dependencies or insert conversions inside them.

A fixed-region metric can own its region and run without a public spatial argument. A client-selected graph declares spatial arguments along each forwarding path. Return a boundary as a GeoDataFrame dependency when another node needs it.

Plugins own coverage checks, reprojection, joins, and area calculations. `lyra.utils.geometry.calculate_feature_areas_m2` is available when it matches the calculation’s needs.

## Inspect the graph

After regenerating the manifest, export a Mermaid diagram:

```sh
uv run lyra-plugin diagram --project . --output graph.mmd
uv run lyra-plugin diagram --project . \
  --detailed --output graph.mmd
```

Repeat `--include-manifest your_manifest_path_here` to include dependency plugins. Paths are relative to your working directory. Omit `--output` to write to standard output.

The diagram command reads saved manifests. Regenerate each manifest after changing its contract. The detailed view adds declared columns, types, units, geometry columns, and dependency input mappings.

## Declare derived location bindings

Use `LocationDependency` to declare an operation result as an internal location argument. Lyra executes nested operations before invoking the receiving node. Bindings can nest:

```python
from lyra.sdk import Dependency, Input, LocationDependency

records = Dependency(
    "street_records", producer="street_records",
    locations={
        "streets": LocationDependency(
            "select_streets",
            locations={
                "region": LocationDependency(
                    "buffer_region",
                    locations={"source": Input("lots")},
                    parameters={"distance": 100},
                )
            },
            parameters={"year": Input("parameters.year")},
        )
    },
)
```

Every `Input` in this tree refers to the effective inputs of the metric or operation that owns `records`. Explicit bindings take precedence over forwarding inputs with matching names. Derived locations do not add public request fields.

When an operation evaluates its own `inputs` declarations, their references use that operation’s effective inputs. [Derive locations inside a graph](../location-operations/) demonstrates this rule with a nested selection binding.

Parameter bindings treat JSON objects as whole literal values. Keys that resemble a reference or operation declaration do not change that behavior.
