Declare a dependency when your calculation needs a table from another metric. For example, the maintenance report needs street lengths and condition scores, which other reports can also reuse. Lyra runs the required calculations and passes their tables to your function.

The metric supplying a table is its producer; the metric receiving it is its consumer. You’ll connect them by naming the producer, its output table, and the argument that receives it. This example uses the city project’s bundled data and requires no service.

## Declare the table graph

In the [prepared city project](../tutorial/), create `maintenance_graph.py` with these imports:

```python title="maintenance_graph.py"
import pandas as pd
from lyra.data import Locations
from lyra.runtime.local import LocalRunner
from lyra.sdk import Dependency, PluginDefinition, metric
from city_example.calculations import calculate_maintenance
from city_example.metrics import (
    MaintenanceParameters, street_conditions, street_lengths,
)
from city_example.provider import CityLocationProvider
from city_example.schemas import MAINTENANCE, STREETS
```

Add the maintenance metric below. Its `inputs` declaration requests the length and condition tables and maps them to the handler arguments `lengths` and `conditions`:

<CodeExample path="examples/city-plugin/city_example/metrics.py" region="maintenance" lang="python" title="maintenance_graph.py" meta="{5-8,14-15,23}" />

The condition metric is private because callers only need its table as part of another calculation. All three metrics declare the same requirements for `streets`, so Lyra passes the selected streets to both producers by name. Only the maintenance calculation uses the threshold to decide which streets need work.

## Register and run the graph

Append the producer registrations, provider, and request:

```python title="maintenance_graph.py"
plugin = PluginDefinition(
    metrics=[street_lengths, street_conditions, street_maintenance],
    resources={"city_data": CityLocationProvider},
    location_provider="city_data",
)
runner = LocalRunner.from_definitions({"city": plugin})
tables = runner.run("city_street_maintenance", {
    "streets": {
        "collection": "example:city", "unit_type": "street",
        "ids": ["street-1"],
    },
})
```

Run `uv run python maintenance_graph.py`. `tables["maintenance"]` identifies `street-1` and reports 100 m of maintenance workload: its score of 20 is below the default threshold of 50. Lyra calculates the dependencies before calling the maintenance handler and reuses identical invocations within a run.

Dependencies can cross plugins without importing their implementations; enable every required producer plugin.

## Forward or rename parameters <span id="3-forward-or-rename-parameters"></span>

A dependency may need a setting such as a survey year. Lyra chooses each producer parameter in this order:

1. An explicit override in the dependency declaration
2. The consumer’s value for a parameter with the same name, including its default
3. The producer’s own default
4. Failure, if a required value is still missing

Lyra forwards parameter values automatically when the names match. For a producer that accepts `year`, a consumer can explicitly map its own `baseline_year` field as follows:

```python
from lyra.sdk import Dependency, Input

inputs = {
    "records": Dependency(
        "example_selected_records", producer="example_selected_source",
        parameters={"year": Input("parameters.baseline_year")},
    ),
}
```

An `Input` path refers to a field declared by the metric or operation that owns the dependency declaration.

Use `parameters=` to supply settings and `locations=` to supply locations to a dependency. Parameter overrides replace whole fields, including nested objects, and explicit `None` counts as a supplied value. Bindings cannot supply tables or contexts.

## Forward the required spatial inputs <span id="4-forward-the-required-spatial-inputs"></span>

If connected metrics use different argument names for the same locations, tell Lyra how they match. Lyra checks these explicit mappings before forwarding inputs with matching names. To supply a producer’s `streets` input from a consumer’s `selected_streets` selection, declare:

```python
locations={"streets": Input("selected_streets")}
```

Declare both names as location inputs on their respective metrics. A consumer may declare an input solely to forward it to a dependency.

Use `Input` references or nested `LocationDependency` declarations for location bindings. Bindings cannot supply literal values. If names differ, declare a binding even when both arguments use `Locations`.

Supplied locations must match the receiving input’s concrete location contract, whether you bind them explicitly or forward matching names. For nested operations, declare that contract as the operation’s output. Lyra rejects incompatible contracts during graph validation.

When callers select blocks for a street metric, canonical selection first converts those blocks to the streets that metric needs. Lyra then forwards those streets to its dependencies. It does not insert additional conversions between calculations; declare those with location dependencies.

If your metric always uses the same region, it can load that region without asking callers to select locations. If callers choose the region, declare a location input on each calculation that receives the selection. When another calculation needs a boundary as a table, return it through a GeoDataFrame dependency.

Your plugin implements coverage checks, reprojection, joins, and area calculations. `lyra.utils.geometry.calculate_feature_areas_m2` is available when it matches the calculation’s needs.

## Inspect the graph

After regenerating the manifest, export a Mermaid diagram:

```sh
uv run lyra-plugin diagram --project . --output graph.mmd
uv run lyra-plugin diagram --project . \
  --detailed --output graph.mmd
```

Repeat `--include-manifest your_manifest_path_here` to include dependency plugins. Paths are relative to your working directory. Omit `--output` to write to standard output.

The diagram command reads saved manifests. Regenerate each manifest after changing its contract. The detailed view adds declared columns, types, units, geometry columns, and dependency input mappings.

## Declare derived location bindings

Use `LocationDependency` when a calculation needs locations derived by another operation. For example, you might buffer selected lots, find streets within that region, and pass those streets to a metric. Lyra runs the operations before calling the function that needs their result:

```python
from lyra.sdk import Dependency, Input, LocationDependency

records = Dependency(
    "street_records", producer="street_records",
    locations={
        "streets": LocationDependency(
            "select_streets",
            locations={
                "region": LocationDependency(
                    "buffer_region",
                    locations={"source": Input("lots")},
                    parameters={"distance": 100},
                )
            },
            parameters={"year": Input("parameters.year")},
        )
    },
)
```

Every `Input` in this example refers to the inputs of the metric or operation that declares `records`, including applied defaults. Explicit bindings take precedence over forwarding inputs with matching names. Derived locations do not add public request fields.

Inside an operation’s own `inputs` declarations, `Input` references use that operation’s arguments, including defaults. [Derive locations inside a graph](../location-operations/) demonstrates this rule with a nested selection binding.

Parameter bindings treat JSON objects as whole literal values. Keys that resemble a reference or operation declaration do not change that behavior.
