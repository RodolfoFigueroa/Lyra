Declare a dependency to use one metric’s output table in another metric. Lyra runs the producer first and passes its table to the consuming function. Both metrics remain available for direct execution.

The example connects a metric that reads census records to a metric that consumes those records. Your plugin supplies the census view; it is not a Lyra database table. The [graph tests](../testing/#test-the-complete-graph) use a fake database to run this example without services.

<Steps>

1. ## Declare a producer <span id="1-declare-a-producer"></span>

   Decorate acquisition functions with `@metric`. Name each output table and declare its columns.

   Create `population_graph.py` with the imports, year model, and shared output declaration:

   ```python title="population_graph.py"
   from typing import Annotated

   import pandas as pd
   from lyra.sdk import (
       DatabaseIO, Dependency, MetricParameters, PluginDefinition,
       Resource, TableColumn, TableOutput, Unit, metric,
   )
   from pydantic import Field

   class Year(MetricParameters):
       year: int = Field(default=2020, description="Census observation year.")

   population_output = TableOutput(columns=[
       TableColumn(
           name="area_code", type="string", unit=None,
           description="Source census area identifier.",
       ),
       TableColumn(
           name="population", type="integer", unit=Unit.COUNT,
           description="Residents in the source census area.",
       ),
   ])
   ```

   Append the metric function, using a bound parameter for the selected year:

   ```python title="population_graph.py" {4,8,10-14}
   @metric(
       name="example_city_source",
       description="Read the plugin’s fixed-city census view.",
       outputs={"example_city_records": population_output},
   )
   def city_source(
       parameters: Year,
       database: Annotated[DatabaseIO, Resource("database")],
   ) -> pd.DataFrame:
       return database.query_dataframe(
           "SELECT area_code, population FROM example_city_census "
           "WHERE year = :year ORDER BY area_code",
           params={"year": parameters.year},
       )
   ```

   Other nodes request this table by its output name, `example_city_records`. Lyra passes the database resource to your function; your plugin defines the query and its output columns.

   Metrics can acquire data directly or consume other metrics’ outputs. HTTP clients, Earth Engine expressions, raster processing, and file readers are implementation choices inside those nodes. Their graph outputs are tables.

1. ## Request the output by name <span id="2-request-the-output-by-name"></span>

   The consuming metric declares a local input argument and the producer output:

   ```python title="population_graph.py" {4}
   @metric(
       name="example_city_population",
       description="Population of the plugin’s fixed city by source area.",
       inputs={"records": Dependency("example_city_records")},
       outputs={"example_city_population": population_output},
   )
   def city_population(parameters: Year, records: pd.DataFrame) -> pd.DataFrame:
       return records

   plugin = PluginDefinition(nodes=[city_source, city_population])
   ```

   Put this mapping in the metric decorator and accept `records` in the handler. The local name becomes a Python keyword argument. The dependency string names an explicit output, so a node name is not an implicit substitute.

   `PluginDefinition` registers both functions. Run `example_city_source` with `{"parameters": {"year": 2020}}` to retrieve its records directly. Run `example_city_population` with the same input to execute both metrics in dependency order.

   Dependencies can also cross plugins without importing the producer’s Python module. Enable all required plugins in your deployment or local runner.

1. ## Forward or rename parameters <span id="3-forward-or-rename-parameters"></span>

   A producer’s ordinary fields resolve in this order:

   1. An explicit override in the dependency declaration
   2. A matching effective parameter on the consumer, including its defaults
   3. The producer’s own default
   4. Failure, if a required value is still missing

   The fixed-city example uses the same `year` name throughout, so it forwards automatically. To rename a public `baseline_year` to the producer’s `year`, use:

   ```python
   from lyra.sdk import Dependency, Input

   inputs = {
       "records": Dependency(
           "example_selected_records",
           arguments={"parameters": {"year": Input("parameters.baseline_year")}},
       ),
   }
   ```

   An `Input` path refers to a directly declared field on the current node. It does not reach back to an arbitrary root request.

   Overrides replace whole fields, including nested objects. Explicit `None` is a supplied value. The `arguments` mapping accepts only `parameters`; tables, contexts, and spatial arguments are supplied through their own mechanisms.

1. ## Forward the required spatial inputs <span id="4-forward-the-required-spatial-inputs"></span>

   Lyra forwards required `location` and `bounds` unchanged by name and kind. Declare each dependency’s required spatial inputs on the consuming metric, even if its calculation only uses tables.

   A fixed-region metric can own its region and run without a public spatial argument. A client-selected graph declares spatial arguments along each forwarding path. A boundary needed by another node can itself be a GeoDataFrame dependency.

   Plugins own coverage checks, reprojection, joins, and area calculations. `lyra.utils.geometry.calculate_feature_areas_m2` is available when it matches the calculation’s needs.

</Steps>

## Inspect the graph

After regenerating the manifest, export a Mermaid diagram:

```sh
uv run lyra-plugin diagram --project examples/lyra-plugin --output graph.mmd
uv run lyra-plugin diagram --project examples/lyra-plugin \
  --detailed --output graph.mmd
```

Repeat `--include-manifest your_manifest_path_here` to include dependency plugins. Paths are relative to your working directory. Omit `--output` to write to standard output.

The diagram command reads saved manifests. Regenerate each manifest after changing its contract. The detailed view adds declared columns, types, units, geometry columns, and dependency input mappings.

Read [how graphs execute](../../concepts/graphs/) for reuse, ordering, and failure behavior. Use [runtime services](../runtime/) for database and Earth Engine access, and [testing](../testing/) to replace sources with fakes.
