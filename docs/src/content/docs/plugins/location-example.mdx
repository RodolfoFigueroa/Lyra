Build an in-memory graph that totals residents from selected lots into selected blocks. You need the repository’s Python environment from [Install Lyra for Python](../../start/installation/). This example uses point locations and string IDs. Fixture properties identify each lot’s parent block.

To derive a dependency’s locations internally, follow [Derive locations inside a graph](../location-operations/).

<Steps>

1. ## Define a fixture provider

   A provider resolves IDs into features. Create `location_example.py` with the imports used throughout this tutorial:

   ```python title="location_example.py"
   from typing import Annotated

   import geopandas as gpd
   import pandas as pd
   import pandera.pandas as pa
   from pydantic import Field
   from pandera.engines.geopandas_engine import Geometry
   from shapely.geometry import Point
   ```

   Import the types and decorators for the provider and metrics. You’ll use `LocalRunner` to run the graph.

   ```python title="location_example.py"
   from lyra.runtime.local import LocalRunner
   from lyra.sdk import (
       Dependency,
       Input,
       LocationDependency,
       LocationProvider,
       PluginDefinition,
       metric,
   )
   ```

   Define block and lot records. These properties establish the example’s relationship and resident counts:

   ```python title="location_example.py"
   records = {
       "block": {"block-a": {}},
       "lot": {
           "lot-x": {"parent_block_id": "block-a", "population": 3},
           "lot-y": {"parent_block_id": "block-a", "population": 5},
       },
   }
   ```

   Append a helper that returns each requested ID, its properties, and point geometry in a `GeoDataFrame`:

   ```python title="location_example.py"
   def features(unit_type, ids):
       frame = gpd.GeoDataFrame(
           [
               {"location_id": identifier, **records[unit_type][identifier]}
               for identifier in ids
               if identifier in records[unit_type]
           ],
           geometry=[
               Point(0, 0) for identifier in ids
               if identifier in records[unit_type]
           ],
           crs="EPSG:4326",
       )
       return frame
   ```

   Declare the structural columns shared by both providers. Each record needs a unique ID and valid geometry:

   ```python title="location_example.py"
   structural_columns = {
       "location_id": pa.Column(
           str,
           unique=True,
           checks=pa.Check.str_length(min_value=1),
           description="Record ID",
           metadata={"unit": None},
       ),
       "geometry": pa.Column(
           Geometry(crs="EPSG:4326"),
           checks=pa.Check(
               lambda values: values.is_valid & ~values.is_empty,
               name="valid_geometry",
           ),
           description="Record geometry",
           metadata={"unit": None},
       ),
   }
   ```

   Use those columns in both schemas. Pass each provider’s additional columns to `location_schema` with their descriptions and units.

   ```python title="location_example.py"
   def location_schema(**properties):
       return pa.DataFrameSchema(structural_columns | properties, strict=True)
   ```

   Define the lot attributes. Each lot belongs to one block, and its population counts residents.

   ```python title="location_example.py" {3,6}
   lot_schema = location_schema(
       parent_block_id=pa.Column(
           str, description="Parent block ID.", metadata={"unit": None}
       ),
       population=pa.Column(
           int, description="Residents in this lot.", metadata={"unit": "count"}
       ),
   )
   ```

   Declare one provider per dataset. Lyra validates every returned frame against the provider’s schema and checks that the IDs match the request exactly.

   ```python title="location_example.py"
   class Blocks(LocationProvider):
       id = "example_blocks"
       code_revision = "1"
       schema = location_schema()

       def resolve(self, ids):
           with self.operation("resolve"):
               return features("block", ids)


   class Lots(LocationProvider):
       id = "example_lots"
       code_revision = "1"
       schema = lot_schema

       def resolve(self, ids):
           with self.operation("resolve"):
               return features("lot", ids)
   ```

   This provider uses in-memory records. Service-backed providers acquire clients in `setup()` and release them in `close()`.

1. ## Declare the lot producer

   A producer is a metric whose output another metric uses. In `lot_output`, use `None` for the block ID and `"count"` for the number of residents.

   ```python title="location_example.py" {7,12}
   lot_output = pa.DataFrameSchema(
       strict=True,
       columns={
           "block_id": pa.Column(
               "str",
               description="Parent block identifier.",
               metadata={"unit": None},
           ),
           "population": pa.Column(
               "int64",
               description="Number of residents in the selected lots.",
               metadata={"unit": "count"},
           ),
       }
   )
   ```

   The producer reads fixture properties without changing its location input. Describe the required properties so callers can select suitable data:

   ```python title="location_example.py"
   @metric(
       code_revision="1",
       inputs={"location": LocationDependency(provider=Lots.id)},
       name="lot_population",
       description="Read residents from selected lots.",
       outputs={"lot_records": lot_output},
   )
   ```

   Append the handler immediately after its decorator. Read each lot’s parent block and population into the output table:

   ```python title="location_example.py"
   def lot_population(
       location: Annotated[
           gpd.GeoDataFrame,
           Field(
               description="Lots with parent_block_id and integer population.",
           ),
       ],
   ) -> pd.DataFrame:
       return pd.DataFrame(location[["parent_block_id", "population"]]).rename(
           columns={"parent_block_id": "block_id"}
       )
   ```

1. ## Bind lots and select blocks

   The consumer metric uses the producer’s table. Bind its `lots` input to the producer’s `location` input. Append the decorator first:

   ```python title="location_example.py" {6-11}
   @metric(
       code_revision="1",
       name="block_population",
       description="Total residents in supplied lots for each selected block.",
       inputs={
           "blocks": LocationDependency(provider=Blocks.id),
           "lots": LocationDependency(provider=Lots.id),
           "records": Dependency(
               "lot_records",
               producer="lot_population",
           ).bind(location=Input("lots")),
       },
       outputs={"block_totals": lot_output},
   )
   ```

   Append the decorated function immediately after that block. It joins by `parent_block_id` through the producer’s `block_id` column:

   ```python title="location_example.py"
   def block_population(
       blocks: Annotated[
           gpd.GeoDataFrame,
           Field(
               description="Blocks whose IDs identify the requested output rows.",
           ),
       ],
       lots: Annotated[
           gpd.GeoDataFrame,
           Field(
               description="Lots needed for the selected block totals.",
           ),
       ],
       records: pd.DataFrame,
   ) -> pd.DataFrame:
       totals = records.groupby("block_id")["population"].sum()
       return pd.DataFrame(
           [
               {
                   "block_id": identifier,
                   "population": int(totals.get(identifier, 0)),
               }
               for identifier in blocks.location_id
           ]
       )
   ```

   Callers must supply every lot needed for their calculation. This example totals only supplied lots and returns zero for a block with no supplied lots. Lyra resolves exact IDs. Check in your application that the selected lots cover the blocks you want to measure.

1. ## Run with ID selections

   Register the metrics and provider as separate definitions. The provider-only plugin has no metric nodes:

   ```python title="location_example.py"
   plugin = PluginDefinition(metrics=[lot_population, block_population])
   provider = PluginDefinition(
       resources={"blocks": Blocks, "lots": Lots},
   )
   request = {
       "blocks": {
           "provider": "example_blocks",
           "ids": ["block-a"],
       },
       "lots": {
           "provider": "example_lots",
           "ids": ["lot-x", "lot-y"],
       },
   }
   ```

   Run the graph and check that the selected lots total eight residents:

   ```python title="location_example.py" {4}
   runner = LocalRunner.from_definitions(
       {"metrics": plugin, "geography": provider},
   )
   tables = runner.run("block_population", inputs=request).tables
   assert tables["block_totals"].to_dict("records") == [
       {"block_id": "block-a", "population": 8},
   ]
   ```

   Run `uv run python location_example.py`. The runner resolves selections and runs both handlers in one resource scope, closing the provider when execution ends. The handlers receive native `GeoDataFrame` values; the public request contains ID selections.

   For server execution, install and enable both plugin definitions before submitting a request:

   - [HTTP](../../use/rest-api/) and [Model Context Protocol (MCP)](../../use/mcp/): submit `{"metric": "block_population", "inputs": request}`
   - Python client: call `client.jobs.submit("block_population", inputs=request)`

   Workers resolve both selections during execution.

   A matching location name forwards automatically. The explicit binding above takes precedence and preserves the lot provider scope. The producer’s identity uses those effective inputs under `location`; changing only `blocks` does not change that identity.

   To test a service-backed provider, pass a fake subclass through `resource_overrides={"lots": FakeLots}`. Keep all acquisition in memory. For direct handler tests, construct native `GeoDataFrame` fixtures and supply dependency tables yourself, as described in [Test a plugin](../testing/).
