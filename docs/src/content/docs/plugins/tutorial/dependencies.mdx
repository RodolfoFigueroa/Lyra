The maintenance calculation needs each street’s length and condition score. Other reports may need those same values, so you’ll make them separate metrics that those reports can reuse. Start with [the parameterized adapter](../parameters/) and its passing tests; the maintenance results should stay the same.

A dependency declares that one calculation needs a table from another. The metric supplying the table is its producer; the metric receiving it is its consumer. Together, these connections form a dependency graph.

<MaintenanceDependenciesDiagram />

Both the length and condition metrics use the selected streets. Lyra runs those dependencies before the maintenance handler and passes their tables into its `lengths` and `conditions` arguments. The threshold goes to the maintenance calculation because that is where the decision about work happens.

The arrows show required data, not parallel execution: Lyra executes dependencies sequentially. When several calculations request the same metric with the same inputs within one run, Lyra reuses its result. You don’t need to call the producer functions or manage that reuse yourself.

1. ## Register your graph

   Add this factory to `city_example/tutorial.py` so Lyra can find all three metrics and their provider. The factory takes no arguments and returns their plugin definition:

   ```python title="city_example/tutorial.py" {3}
   def create_plugin() -> PluginDefinition:
       return PluginDefinition(
           metrics=[street_lengths, street_conditions, street_maintenance],
           resources={"city_data": CityLocationProvider},
           location_provider="city_data",
       )
   ```

   Create `run_tutorial.py` in the project root. Import your factory and submit the same street selection:

   ```python title="run_tutorial.py"
   from lyra.runtime.local import LocalRunner
   from city_example.tutorial import create_plugin

   runner = LocalRunner.from_definitions({"city": create_plugin()})
   tables = runner.run("city_street_maintenance", {
       "streets": {
           "collection": "example:city", "unit_type": "street",
           "ids": ["street-3", "street-1"],
       },
   })
   print(tables["maintenance"].to_dict("records"))
   ```

   Run `uv run python run_tutorial.py`. With the default threshold, `street-3` contributes 300 m and `street-1` contributes 100 m. `uv run python -m city_example 4` runs the supplied reference checkpoint for comparison.

1. ## Verify that the refactoring preserves results

   Create `tests/test_tutorial.py` to run both versions with the same request. Comparing their tables checks that introducing dependencies has not changed the maintenance policy or row identities:

   ```python title="tests/test_tutorial.py" {16-18}
   from lyra.runtime.local import LocalRunner
   from city_example.tutorial import create_plugin
   from maintenance_metric import plugin as direct_plugin


   def test_dependencies_preserve_the_direct_result():
       request = {
           "streets": {
               "collection": "example:city", "unit_type": "street",
               "ids": ["street-3", "street-1"],
           },
           "parameters": {"condition_threshold": 40},
       }
       direct = LocalRunner.from_definitions({"city": direct_plugin})
       graph = LocalRunner.from_definitions({"city": create_plugin()})
       expected = direct.run("city_street_maintenance", request)["maintenance"]
       actual = graph.run("city_street_maintenance", request)["maintenance"]
       assert actual.equals(expected)
   ```

   Run `uv run pytest tests/test_tutorial.py`. Keep the tests from earlier chapters. Treat dependency tables as read-only: another calculation may receive the same table. Make a copy if you need to change one.
